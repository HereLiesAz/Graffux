# Brush Stroke Mechanics Roadmap

This document is the **primary implementation roadmap for stroke realism** in Graffux.

The existing `Material-Aware Paint Engine Roadmap.md` remains useful supporting research, but material behavior is secondary. The critical path here is limited to behavior that changes because of the brush and the way the stroke is made.

## Scope boundary

### In scope — brushstroke-specific mechanics

- stroke speed and acceleration;
- rake / drag direction;
- directional bending;
- angular lag behind the hand;
- contact hysteresis / mechanical memory;
- snap-back and recovery;
- touchdown, dwell, stab, drag, flick and lift-off behavior;
- coarse bristle bundles / sub-tufts;
- bristle splay;
- coherent split tips;
- structured rake/comb striation generated by brush geometry;
- flat / round / filbert / rigger / fan-like morphology;
- pressure as a later driver of contact/compression/splay;
- stylus tilt as a later driver of brush lean/contact geometry;
- stylus orientation as a later driver of brush orientation/rake intent;
- deterministic replay of all mechanical state;
- live/commit/GPU parity for the resulting dab/tuft geometry;
- bounded mobile cost.

### Explicitly not on the primary path

These may interact with brush mechanics later, but they are not brushstroke mechanics and must not drive the current implementation sequence:

- pigment/color mixing;
- wet-paint transfer and reservoir chemistry;
- fluidity, viscosity and flow simulation;
- canvas/substrate surface texture or absorbency;
- wetness transport;
- diffusion/bleeding;
- impasto/material height evolution;
- optical wet/dry shading;
- spectral/Kubelka-Munk work.

Brush-tip texture that emerges from **bristle/tuft geometry** is in scope. Canvas surface texture is not.

---

## Governing distinction: brush physics first, intent inference second

Pressure, tilt and orientation are brushstroke-specific inputs, but they are best treated as **evidence of the artist's intended contact state**, not as a substitute for the brush mechanics themselves.

Therefore the implementation order is:

```text
1. Build a brush that can bend, drag, lag, recover, splay, split and lift mechanically.
2. Make those mechanics deterministic and renderer-independent.
3. Then let pressure / tilt / orientation steer that mechanical system.
```

The wrong order would be:

```text
pressure -> radius
 tilt    -> aspect ratio
 azimuth -> angle
```

with no actual brush state underneath. That produces a responsive stamp, not a mechanically convincing brush.

The target is instead:

```text
artist motion + stroke lifecycle
        ↓
brush mechanical state
        ↓
contact / tuft geometry
        ↓
resolved dabs

then, once stable:

pressure / tilt / orientation
        ↓
intent interpretation
        ↓
mechanical targets / forces
        ↓
that same brush mechanical state
```

---

## Current mechanical baseline

Graffux already provides:

- canonical `BrushSample` input with pressure, tilt, orientation, speed, distance, drawing angle and touch-major;
- deterministic `BrushSensorEngine` routes;
- dynamic size, opacity, flow, spacing, scatter, rotation, hardness and tip-ratio resolution;
- speed-sensitive thinning;
- speed-adaptive start/end behavior;
- first-touch blot, dwell growth and sharpness response;
- elongated tips and per-dab angle;
- follow-stroke rotation;
- incremental live dab generation;
- matching commit/replay generation;
- CPU and Vulkan renderers that consume already-resolved dab geometry.

That gives us enough infrastructure to improve mechanics **before** inventing another renderer.

## Mechanical architecture

```text
BrushSample
    ↓
Stroke Kinematics
(speed, heading, acceleration, lifecycle)
    ↓
Brush Mechanical State
    ↓
Brush Contact / Tuft State
    ↓
Resolved Dab / Tuft Geometry
    ↓
Existing CPU / Vulkan Renderer
```

Later, intention inference is inserted without replacing the model:

```text
Pressure / Tilt / Orientation
    ↓
Intent Resolver
    ↓
Mechanical Targets
    ↓
Brush Mechanical State
```

### Brush Mechanical State

Persistent within one stroke:

- bend direction;
- bend magnitude;
- angular lag;
- drag direction;
- recovery/snap state;
- hysteresis / previous deformation;
- splay state;
- optional per-tuft displacement and separation.

### Brush Contact / Tuft State

Renderer-independent output:

- contact center/offset;
- width/radius multiplier;
- aspect ratio;
- contact angle;
- splay;
- sub-tuft positions/angles/weights;
- split/cohesion state.

Renderers consume this resolved geometry. They do not implement brush mechanics themselves.

## Phase M1 — Stateful bend, drag, lag and recovery

**Goal:** stop treating every dab as an independent footprint.

This phase uses only stroke kinematics and lifecycle information that already exist independently of pressure/tilt/orientation:

- drawing direction;
- speed;
- acceleration/deceleration;
- elapsed time;
- distance;
- touchdown / movement / stopping / lift lifecycle.

Add a small deterministic stroke-local state:

- current bend vector;
- target drag direction;
- bend magnitude;
- stiffness;
- damping;
- angular lag;
- recovery toward rest;
- directional hysteresis.

Expected behavior:

- a soft brush trails a direction change;
- a stiff brush follows quickly;
- faster motion bends farther;
- slowing down reduces bend;
- stopping allows recovery;
- reversing direction produces a transient flip/snap instead of an angle teleport;
- the brush can remember its prior contact orientation across consecutive dabs.

### Exit gate

- deterministic state evolution;
- O(new dabs), never O(total stroke history);
- visible speed-dependent bend and lag;
- visible reversal hysteresis;
- live/commit agreement;
- disabled configuration exactly preserves the current path.

---

## Phase M2 — Coarse bristle / tuft topology

**Goal:** give the brush real internal contact structure instead of one deforming ellipse.

Represent the tip as a small fixed number of sub-tufts/bundles.

Each bundle may have:

- ferrule-local root offset;
- rest direction;
- stiffness;
- current bend/contact offset;
- neighbor cohesion;
- local width/contact weight.

This phase is geometric. It does **not** depend on paint load, canvas texture or fluid simulation.

Mechanical outputs:

- coherent tuft movement;
- bundle-level drag;
- splay;
- separation;
- split tips;
- snap-back;
- stable parallel marks.

### Algorithm progression

1. analytic bundle layout;
2. damped spring/contact approximation;
3. constrained/PBD bundle solver only if the analytic/spring model visibly fails;
4. individual-bristle simulation only if bundle mechanics still fail.

### Exit gate

- split marks remain structurally coherent across a stroke;
- no pure-random scatter masquerading as bristles;
- deterministic bundle identities across replay;
- bounded bundle count / capability tiers.

---

## Phase M3 — Rake / drag mechanics and brush archetypes

**Goal:** make brush morphology and drag direction produce recognizably different strokes.

Initial archetypes:

- Round;
- Flat;
- Filbert;
- Rigger/Liner;
- Fan;
- Rake/Comb.

Examples:

- **Flat:** broad lateral body, strong rake direction, edge/knife transition.
- **Round:** radial bundle distribution, weaker angular dependence.
- **Filbert:** rounded flat with smoother edge transitions.
- **Rigger:** long lag, narrow footprint, strong trailing behavior.
- **Fan:** wide bundle spread and angle-dependent fan collapse/spread.
- **Rake/Comb:** stable parallel bundle contacts with coherent directional striation.

Rake is a mechanical relation between the tuft arrangement and movement direction, not a texture overlay.

### Exit gate

The same path/speed sequence produces mechanically distinct marks for at least Round, Flat and Rake/Comb before any pressure/tilt/orientation intent mapping is enabled.

---

## Phase M4 — Touchdown, dwell, lift-off and cornering

**Goal:** make contact transitions part of one mechanical system.

Graffux already has useful taper/blot behavior. This phase consolidates and extends it rather than discarding it.

Focus on:

- first-contact compression;
- initial tuft spread;
- dwell growth of contact deformation;
- transition from stab to drag;
- drag settling;
- cornering;
- reversal snap;
- slowing/stopping recovery;
- fast flick exit;
- slow deliberate lift-off;
- tuft convergence during lift.

Existing `BrushBlot`, speed-sensitive thinning and taper behavior must remain compatible or migrate through explicit versioning.

### Exit gate

- touchdown, continuous drag and lift read as one evolving brush contact;
- fast flick and slow lift are mechanically different;
- corners and reversals retain state instead of regenerating an independent stamp orientation.

---

## Phase M5 — Pressure / tilt / orientation intent inference

**Goal:** use stylus telemetry to steer the already-working physical brush model.

This phase comes **immediately after the core brush physics above**.

Pressure, tilt and orientation remain canonical `BrushSample` data, but their role becomes richer than direct parameter mapping.

### Pressure

Interpret as evidence for intended contact/compression:

- target compression;
- target splay;
- contact width/depth;
- possible tuft separation threshold;
- lift/contact confidence.

Pressure should drive the mechanical target, not simply multiply radius or opacity.

### Tilt

Interpret as evidence for brush lean:

- asymmetric contact;
- leading/trailing bundle engagement;
- side-of-brush vs point contact;
- bend bias;
- footprint transition.

### Orientation / azimuth

Interpret as intended ferrule/brush orientation:

- flat-brush edge vs broad-side presentation;
- rake alignment;
- fan direction;
- rest-direction target.

### Fusion rule

Motion remains authoritative evidence too. A tilted/oriented stylus moving in a conflicting direction should not instantly teleport the contact state. Mechanical stiffness, drag and hysteresis mediate the result.

Conceptually:

```text
intentTarget = f(pressure, tilt, orientation, motion)
mechanicalState += responseToward(intentTarget, stiffness, damping, dt)
```

### Exit gate

- pressure changes actual splay/compression state;
- tilt changes which part of the tuft contacts;
- orientation steers brush presentation without bypassing lag/hysteresis;
- disabling intent inference returns to the same M1–M4 mechanical model.

---

## Phase M6 — Native/GPU and performance hardening

Most mechanics should remain renderer-independent and resolve before drawing.

Required gates:

- CPU/Vulkan consume identical resolved geometry;
- no renderer-specific re-interpretation of pressure, tilt, orientation or speed;
- incremental mechanics cost stays bounded with stroke length;
- no unbounded tuft solver queue;
- capability tiers can reduce tuft count or iterations;
- Basic Brush/static path remains the latency baseline.

---

## Immediate implementation tranche

### Tranche M1-A — Mechanical-state contract

1. Add renderer-independent `BrushMechanicalConfig` and `BrushMechanicalState`.
2. Add deterministic incremental state transition logic using:
   - movement heading;
   - speed;
   - time/distance;
   - previous mechanical state.
3. Resolve:
   - drag direction;
   - speed-dependent bend magnitude;
   - stiffness-controlled angular lag;
   - hysteresis on direction changes;
   - recovery toward rest as speed falls.
4. Default configuration is disabled/identity.
5. Integrate the same transition logic into:
   - canonical `BrushStamps.dynamicDabs`;
   - `IncrementalDynamicDabGenerator`.
6. Add golden tests for:
   - disabled compatibility;
   - slow vs fast drag;
   - 90-degree corner lag;
   - 180-degree reversal hysteresis;
   - stop/recovery;
   - live/commit parity.
7. Do **not** use pressure, tilt or orientation yet.
8. Do **not** add material transfer, canvas texture, wetness, color or fluid behavior.

### Tranche M1-B — Tuft geometry foundation

After M1-A passes:

1. add stable sub-tuft identities;
2. map mechanical bend/splay state to bundle contact offsets;
3. emit structured multi-contact geometry;
4. prove deterministic split-tip/rake marks.

### Then: M5 intent inference

Only after the mechanical core can already bend, drag, lag, recover, splay and split coherently do we wire pressure/tilt/orientation into it.

---

## Priority statement

When choosing between a material improvement and a brushstroke-mechanics improvement, **brushstroke mechanics wins unless material work is required to preserve correctness of already-landed behavior**.

Within brushstroke mechanics, **intrinsic brush physics comes before pressure/tilt/orientation intent inference; intent inference follows immediately once that physics exists.**
