# Krita Brush Engine Adoption

Graffux should borrow solved painting-engine ideas from Krita aggressively while keeping a distinctly phone-first product model.

Krita is the reference for mature brush-engine decomposition; Graffux is not trying to reproduce Krita's desktop/tablet interface. The invariant is **Krita underneath, Graffux on top**: deep engine capability, small transient controls, presets, gestures, and progressive disclosure that preserve canvas space on phones.

Every brush-engine tranche has one additional merge gate beyond ordinary unit/build success: it must preserve the phone interaction model. New engine capability may add transient or progressively disclosed controls, but it must not require permanent desktop-style panels or reduce the default drawing area.

## 1. Canonical input telemetry

Graffux normalizes Android input into `BrushSample` before rendering. A sample carries:

- x/y position;
- event time;
- pressure;
- stylus tilt;
- stylus orientation;
- cumulative travelled distance;
- instantaneous speed;
- drawing angle;
- whether the sample is prediction-only.

`BrushSampleBuilder` derives the kinematic fields. Predicted samples are presentation-only and are never allowed to become the basis of the next authoritative sample.

Sensor kinematics remain in physical screen/hand space. Viewport and layer transforms may remap x/y for rasterization, but zooming a canvas must not alter what the brush considers the same physical drawing speed or distance.

## 2. Sensor-to-parameter routing

`BrushSensorDynamics` provides the same important separation used by mature paint engines: input sensors do not directly know about renderers. A sensor is normalized, passed through a response curve, and then routed to a brush parameter.

Current sensors include pressure, speed, tilt, orientation, distance, time, drawing angle, per-dab random, and per-stroke random.

Current targets include size, opacity, flow, spacing, scatter, rotation, hue, saturation, value, smudge rate, Color Rate, and smudge radius.

Existing brushes have no routes by default, so their historical rendering path remains unchanged.

## 3. Determinism and replay

Authoritative strokes record canonical brush telemetry alongside the existing path and pressure arrays. Live rendering, commit, undo/redo replay, and future collaboration serialization should consume the same recorded sensor state instead of recomputing it from current device conditions.

Only x/y are transformed into bitmap coordinates during replay. Recorded speed, distance, tilt, orientation, time, and drawing angle remain unchanged.

Seeded random sensors and existing stamp jitter remain deterministic.

Color Smudge settings are snapshotted onto each Smudge `StrokeCommand`. Undo/redo therefore replays the mode, rates, radius, alpha behavior, and sensor routes used when the stroke was made rather than whatever Tool Options contains later.

Stamp brushes now snapshot the primary tip image, grain image, and masked-secondary-tip image into the stroke command as well. Installed brush assets therefore replay independently of whichever brush or extension is selected later.

## 4. Phone-first Brush Studio

The engine may expose many sensors and targets without putting all of them permanently on screen.

Brush Studio keeps its compact floating-window form. Dynamics are collapsed by default and begin with useful mappings such as:

- Pressure → Size
- Pressure → Opacity
- Speed → Thin
- Speed → Spacing
- Tilt → Rotation

Texture and Masked Tip are separate collapsed sections. Common spacing/tip controls remain close to the top of Brush Studio; the canvas is not surrounded by permanent option panels.

Color Smudge follows the same rule: its Smear/Dulling mode, Smudge, Color Rate, radius, opacity and alpha-carry controls appear only in the transient Tool Options window while Smudge is active.

Phone-specific inputs should be treated as first-class opportunities: finger velocity, temporary thumb controls, long-press modifiers, device orientation where useful, and transient HUDs that disappear while painting.

## 5. CPU and Vulkan contract

`BrushStamps.dynamicDabs` resolves geometry and per-dab paint dynamics into concrete dabs. The Android raster renderer consumes those resolved instructions rather than reimplementing sensor logic.

The Vulkan dab ABI has two compatible paths. Legacy callers keep the original five-field dab plus stroke-level color/alpha push constants. Dynamic callers use the widened resolved-dab record with per-dab RGBA and flow. The shader selects the widened fields only when the dab marks itself resolved, so static brushes retain their established path while flow/H/S/V dynamics can stay on Vulkan.

`stamp.comp` is authoritative and its embedded `StampSpv.h` is regenerated by NDK `glslc` during CMake configure, preventing source/SPIR-V drift.

Color Smudge has its own persistent Vulkan read/modify/write compute path on the same layer image. The CPU engine remains the correctness/reference fallback. A stroke uploads once, executes its ordered Smudge plans on the GPU, and reads back once at commit rather than round-tripping pixels for every dab.

The new tip-ratio, grain, and masked-tip pipeline is deliberately CPU-first. Ordinary round/image brushes retain their established fast paths; advanced mask/texture brushes fall back to the correctness renderer until the later GPU-resident mask/texture tranche implements equivalent semantics.

## 6. Color Smudge

Graffux's Smudge tool performs directional color carry and is not a blur. The generalized Color Smudge engine follows the same high-level decomposition proven by Krita.

### Smear

Carry the sampled source region from the previous dab toward the current dab. Graffux's historical directional smudge is retained as the compatibility/default preset and is protected by pixel-equivalence tests.

### Dulling

Sample a weighted color beneath the brush over a configurable smudge radius, then mix/fill the current dab with that sampled color while preserving the brush mask.

### Color Rate

Deposit the current foreground paint separately from the smudge stage. Smudge strength and paint deposition are independently controllable so a brush can range from pure smudge through wet mixing to ordinary paint with a small amount of pickup.

### Color Smudge settings

- mode: Smear or Dulling;
- smudge rate;
- color rate;
- smudge radius;
- opacity;
- alpha carry behavior;
- optional sensor/response-curve routes for Smudge Rate, Color Rate, Smudge Radius and shared opacity.

The existing `Tool.SMUDGE` default maps to Smear with zero Color Rate.

## 7. Color Smudge implementation order

1. **Done:** factor the current directional smudge into a reusable Color Smudge engine without changing compatibility output.
2. **Done:** preserve the current smudge test suite as compatibility coverage.
3. **Done:** explicit Smear tests for direction, alpha, strength, and flat-color invariance.
4. **Done:** Dulling with weighted color sampling and radius behavior.
5. **Done:** independent Color Rate/deposition and mixed-pigment behavior.
6. **Done:** route Color Smudge parameters through the shared sensor/curve resolver and recorded physical telemetry.
7. **Done:** move the correct CPU implementation to a persistent Vulkan read/modify/write path with CPU fallback/reference parity.
8. **Implemented, awaiting physical-device data:** the Vulkan engine carries both 8x8 and 16x16 compute variants, benchmarks them on the active Vulkan vendor/device, caches the selected tile size for that device, and exposes an instrumentation parity/benchmark test. Actual Adreno and Mali benchmark results still require running that instrumentation on representative physical devices; no such result is claimed here.

The build gate compiles and links both ARM native targets, but build success is not treated as a substitute for running the instrumentation on physical Adreno/Mali hardware.

## 8. Spacing, tip masks, texture, and masked brushes

This tranche adopts four closely related Pixel Brush Engine ideas as one coherent pipeline.

### Spacing

**Implemented:** spacing can remain isotropic/diameter-based for historical compatibility or become ratio-aware for elongated tips. Sensor-resolved size and spacing affect each successive placement step, so pressure/speed dynamics alter the actual dab cadence rather than merely changing the appearance of fixed centres.

Primary jitter keeps its established random stream. Enabling a masked second tip uses a separate deterministic random stream so secondary scatter cannot perturb primary geometry or replay.

### Brush-tip masks and caching

**Implemented in the CPU correctness renderer:** generated round/elliptical masks and scaled image-tip masks are cached by the raster-affecting parameters rather than regenerated for every dab. Position, color, opacity, flow, and stroke seed remain outside the cache key because they are downstream operations.

Evicted cache entries are not explicitly recycled while a renderer may still hold a reference; Bitmap/GC ownership avoids cross-worker recycled-bitmap races between live preview and history replay.

### Texture / grain

**Implemented in the CPU correctness renderer:** grain is an orthogonal stage after the primary/secondary tip masks are resolved. Brush packages can provide a grain image with:

- scale and strength;
- moving/brush-relative coordinates;
- canvas-locked coordinates;
- deterministic per-stroke phase;
- Multiply, Subtract, Darken, and Overlay-style mask transfer modes.

Moving grain repeats its local relationship to each dab. Canvas-locked grain samples global layer coordinates so the texture remains stationary while the brush moves.

### Masked / dual brush

**Implemented in the CPU correctness renderer:** a brush may own a second independently configured tip with its own shape asset or generated tip, size ratio, tip ratio, hardness, opacity, flow, rotation/follow-stroke behavior, scatter, invert/combine mode, and sensor routes. The secondary tip resolves independently and then masks the primary impression.

This is the common engine primitive needed for both Krita-style Masked Brush behavior and a later richer dual-brush UI. Existing brushes have no secondary tip by default and keep their historical rendering path.

### Phone UI

**Implemented:** ratio/spacing controls remain near Spacing, while Dynamics, Texture, and Masked Tip are collapsed sections. A generated second tip can be enabled without first selecting an external bitmap; installed brush packages may provide primary, grain, and secondary-tip assets.

### Validation requirements

The tranche is protected by tests for legacy spacing compatibility, ratio-aware placement, dynamic spacing, independent primary/secondary random streams, secondary sensor dynamics, tip-mask cache reuse, elliptical raster geometry, moving versus canvas-locked grain phase, masked-tip clipping, and deterministic repeated rendering.

## 9. Next Krita-derived tranches

The next work after this foundation is validated and merged is:

1. Color Source + Mix: foreground/background interpolation, gradients, deterministic per-dab color sources, and sensor-routed mixing.
2. General taper/fade/lift-off: start/end size and opacity taper, time/distance fade, and phone-specific velocity-derived lift-off for finger input.
3. Scatter/rotation refinement: longitudinal/perpendicular scatter semantics, distance rotation, and richer angle sensors shared by primary and secondary tips.
4. Overlay/all-layer Color Smudge sampling with a separate read-only composite sampling surface.
5. Paint thickness/impasto state alongside color.
6. Airbrush/build-up timing and wash/build-up semantics.
7. Brush preset interoperability once Graffux can represent the required primitives faithfully.
8. GPU-resident brush-mask/texture/secondary-tip execution with CPU reference parity.
9. Dirty-tile/region rendering and tile-based undo snapshots.

## 10. Non-negotiable architecture rules

- Prediction is disposable presentation state, never authoritative paint.
- Recorded physical gesture telemetry is deterministic replay data.
- View transforms alter geometry, not hand-motion sensor meaning.
- Static brushes keep their established rendering path unless an advanced feature requires the correctness pipeline.
- Brush behavior is resolved before renderer-specific code wherever practical.
- CPU and GPU paths must produce equivalent visible behavior.
- Randomness that belongs to an optional stage must not perturb unrelated stage randomness.
- Texture coordinates and tip coordinates are separate concepts.
- Engine power must not turn the phone interface into a desktop control panel.
